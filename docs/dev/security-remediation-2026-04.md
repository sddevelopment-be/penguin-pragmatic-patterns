## Context

All 69 alerts are in **build-time and test-time tooling**, not in shipped site assets. The
published output of this repository is a static HTML/CSS site generated by Hugo. No JavaScript
from `validation/` or Maven test code reaches the browser. Risk to site visitors is zero.
Nonetheless, compromised build tooling can affect CI integrity, supply-chain pipelines, and
developer machines, so remediation remains worthwhile.

## Remediation Steps

### Step 1 — npm automated fix (Build-Automation Brett)

Run inside the `validation/` directory. Most non-breaking fixes are applied automatically.

```bash
cd validation
npm audit fix
npm test   # verify Cypress and other tooling still pass
```

If `npm audit fix` leaves remaining alerts (packages requiring major version bumps), inspect
the remaining audit report:

```bash
npm audit --json | jq '[.vulnerabilities | to_entries[] | {pkg: .key, severity: .value.severity, fixAvailable: .value.fixAvailable}]'
```

For packages where `fixAvailable` is `false` or requires a **breaking change**, evaluate
whether upgrading the *direct* dependency that pulls in the vulnerable transitive package
resolves it. For example, upgrading `sitespeed.io` to the latest release is likely to pull
in a fixed `basic-ftp`, `tar`, and `systeminformation`.

```bash
# Check what version of sitespeed.io is available
npm info sitespeed.io version

# Upgrade sitespeed.io (high impact — pulls in many transitive fixes)
npm install sitespeed.io@latest --save-dev
npm test
```

Similarly, upgrading `cypress` to its latest major may resolve `picomatch` and `minimatch`
alerts, as Cypress bundles both.

### Step 2 — Maven dependency updates (Build-Automation Brett)

These are test-scope dependencies in the Java examples project. They have no runtime impact
on the site but should be kept current.

Edit `src/examples/patterns-base/pom.xml`:

```xml
<!-- assertj-core: 3.17.2 → 3.27.7 (or latest 3.x) -->
<dependency>
    <groupId>org.assertj</groupId>
    <artifactId>assertj-core</artifactId>
    <version>3.27.7</version>
    <scope>test</scope>
</dependency>

<!-- commons-lang3: 3.11 → 3.18.0 (or latest 3.x) -->
<dependency>
    <artifactId>commons-lang3</artifactId>
    <version>3.18.0</version>
    <scope>test</scope>
</dependency>
```

Verify the Java example project still compiles and passes tests:

```bash
cd src/examples/patterns-base
mvn verify
```

### Step 3 — Verify and close alerts

After applying fixes, re-run the full audit to confirm the alert count drops:

```bash
# npm
cd validation && npm audit

# Maven
mvn dependency-check:check   # if dependency-check plugin is configured
```

Dependabot will automatically close resolved alerts once the fix is merged to the default
branch.

## Notes

- **`uuid` major bump (→ 14.0.0):** This is an unusually large version jump. `uuid` v14
  likely has API changes. Check whether the consuming package (possibly `cypress` or a
  lint plugin) has itself updated to use the new API before applying directly.
- **`systeminformation`:** Used by `sitespeed.io`. Upgrading `sitespeed.io` is the
  preferred remediation path over manually pinning `systeminformation`.
- **`lodash`:** Many alerts reference very old versions (4.17.x). If `lodash` appears in
  `npm audit` as a direct dependency at that version, it should be replaced; if transitive,
  the consuming package must be upgraded.
- All npm packages here are `devDependencies` — they are never installed in production
  environments and do not affect site visitors.
